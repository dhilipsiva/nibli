## system

The Modelica ecosystem: Modelica Language Specification (MLS 3.7, May 2026, Modelica Association / MAP-Lang), Modelica Standard Library (MSL 4.1.0), OpenModelica (OSMC, v1.27.0), Dymola (Dassault Systèmes, 2026x), and the FMI standard (3.0.x, Modelica Association Project).

## overlap

Mechanism-level overlap is substantial on the simulation half of the proposed product. Modelica is a typed, declarative, human-readable surface language: models are classes with typed named components (Real/Integer/Boolean/String plus user types with unit/quantity/min/max attributes), acausal equations, and named modification/connection syntax that is close in spirit to predicate calls with named argument places. Compilation is a defined pipeline: static name resolution (undeclared identifiers are compile errors), flattening of the class hierarchy, and reduction to a "flat hybrid DAE" — the MLS 3.7 introduction states semantic restrictions exist precisely so the model can be "transformed into a set of differential, algebraic and discrete equations" (specification.modelica.org/maint/3.7/introduction1.html, accessed 2026-08-26). The compiler's core competency is exactly the proposed product's "orchestrator" premise inverted: symbolic manipulation (matching, index reduction via Pantelides/dummy-derivative, tearing, causalization) producing code that is handed to numerical solvers. FMI is the ecosystem's typed external-solver seam: a compiled model becomes an FMU — a zip with a C API plus an XML model description carrying typed variables with units, capability flags, tolerances, and generating-tool identity — consumed by 280+ tools (fmi-standard.org, accessed 2026-08-26). The MSL is a curated, versioned standard vocabulary (electrical, mechanical, thermal, fluid, control; BSD-3-Clause) analogous to the product's committed corpus. Batch-vs-interactive split also matches practice: translation and checking are interactive; simulation runs are batch jobs. Finally, the ecosystem is now bolting on the product's provenance ambition: SSP Traceability, a layered Modelica Association standard for a "Credible Simulation Process" with standardized documentation and metadata along the simulation chain, was announced for release in 2025 (newsletter.modelica.org 2025-01; nafems.org event pages, accessed 2026-08-26).

## insufficiency

Missing mechanisms, not ambitions: (1) No logical inference or proof objects. Modelica semantics is a hybrid DAE for numeric integration; there is no entailment relation, no query verdict, no derivation object. The spec explicitly does not define how to simulate a model and does not guarantee a model can be initialized or simulated (MLS 3.7 §1.2). (2) No result taxonomy. Outcomes are trajectories or tool-specific diagnostics; nothing like proved/refuted/out_of_regime or a disposition axis exists in MLS or FMI (FMI 3.0 status codes are call-level: fmi3OK/Warning/Discard/Error/Fatal). (3) Unit soundness is fail-open: unit is a string attribute defaulting to "", and the MLS 3.7 unit chapter presents consistency analysis as tool-dependent — it even narrates that "a tool which does not detect the unit conflict might give the unexpected result of x being 5 meters" (specification.modelica.org/maint/3.7/unit-expressions.html, accessed 2026-08-26). Undeclared vocabulary fails closed; missing units, reference frames, and model assumptions do not. (4) No typed empirical evidence: measurements, parameter provenance, and structural/measurement/numerical uncertainty have no language-level representation; annotations are legal carriers but other tools may silently ignore them — the exact fail-open behavior the product forbids. (5) No chemistry/biology identity semantics: species/compound identity lives in library conventions (Chemical, BioChem, Physiolibrary), not the language. (6) Reproducibility receipts: FMU metadata records generationTool/date; there is no standardized source/IR/artifact hash chain, seed/tolerance receipt, or replay instruction; cross-tool numerical determinism is explicitly out of spec scope. (7) Deterministic compilation across implementations does not hold in practice — tools implement different MLS subsets (Dymola 2026x supports MLS 3.6, not 3.7).

## narrowing_history

Partially narrowed, with evidence. The founding ambition (1996–1997, Modelica 1.0) was a single unified language so physical models could be exchanged at source level between all tools — unifying prior languages (Dymola, Omola, NMF, ObjectMath). Two documented retreats: (a) Source-level model exchange between organizations largely failed commercially (IP exposure, tool subset divergence), and the ecosystem's answer was FMI — compiled black-box exchange — created in the MODELISAR ITEA2 project (July 2008–December 2011, 29 partners, Daimler among core developers) explicitly to "simplify the creation, storage, exchange and (re-)use of dynamic system models of different simulation systems" (fmi-standard.org/about/, accessed 2026-08-26). FMI's 280+ tool adoption versus full-Modelica's ~dozen implementations shows where the exchange ambition actually landed. (b) Semantic completeness was never achieved: unit checking, simulation methodology, and numerical behavior remain quality-of-implementation after 29 years and 18 spec releases, so the "one model, same result everywhere" ambition narrowed to "one syntax, tool-dependent semantics at the edges." The core scope (equation-based multi-domain cyber-physical simulation) never narrowed — PDEs, formal verification, and evidence/uncertainty were never in scope and stayed out.

## lessons

Copy: (1) The layered-standards architecture — language spec / standard library / competing implementations / a minimal compiled-artifact exchange format (FMI: small C API + typed XML metadata) — FMI's minimalism is why 280+ tools adopted it while full Modelica has ~a dozen implementations; the proposed product's solver-orchestration seam should look like FMI (typed capability flags, tolerances, tool identity in the artifact) and should probably consume FMUs as one solver backend rather than recompete with 30 years of DAE compiler engineering. (2) A curated, versioned, permissively-licensed standard vocabulary (MSL model) as the corpus. (3) Nonprofit-association governance with a public spec repo and maintenance branches. Avoid: (1) "Quality of implementation" semantics — leaving unit checking, diagnostics, and numerical behavior tool-dependent destroyed cross-tool determinism and made the same model mean different things in different tools; the product's fail-closed, deterministic-compilation stance is the direct negation of Modelica's costliest mistake. (2) Spec without conformance suite or reference implementation — subset divergence (Dymola still on MLS 3.6 as the 3.7 spec ships) is the observable consequence. (3) Bolting provenance on decades later: SSP Traceability arrives ~2025 as documentation-grade metadata because receipts were never in the artifact model; bake receipts into the IR and artifact format from day one. (4) Annotations as fail-open extension points — legal-to-ignore metadata is where evidence and credibility information go to die.

## cluster_answer

No — "Modelica plus a provenance layer" is the honest answer only for the numerical-simulation third of the product, and even there the honest form is "FMI-consuming orchestrator," not "extended Modelica." Mechanism-level gaps: (1) Logical inference/proof objects: absent and not closable by extension — Modelica's semantic target is a flat hybrid DAE for integration; there is no entailment, no verdict, no derivation object, and retrofitting one means a new semantic foundation, not annotations. (2) Typed empirical evidence with separated uncertainties: absent; annotations could carry the data but MLS annotations are ignorable by other tools (fail-open), so the guarantee the product needs cannot be expressed. (3) Provenance/receipts: partially closable — FMU metadata + the new SSP Traceability layered standard (Credible Simulation Process, ~2025) give tool identity and process documentation, but nothing hash-chains source→IR→artifact or standardizes seeds/tolerances/replay; SSP Traceability is a documentation/metadata chain for human audit, not machine-checked receipts. (4) Chemistry/biology identity semantics: library conventions only. (5) Fail-closed vocabulary: identifiers fail closed, but the unit system is the cautionary tale — unit is a string attribute defaulting to unitless "", dimensionless is spelled "1", and MLS 3.7 explicitly treats unit-consistency analysis as tool-dependent, acknowledging a conforming tool may miss a conflict and "give the unexpected result of x being 5 meters." What Modelica guarantees is unit syntax, not unit soundness. DAE index reduction (Pantelides + dummy derivatives, tearing) is the crown-jewel compiler competency, worth ~decades of engineering — the product should reach it through OpenModelica/FMU delegation as a typed backend, never rebuild it. Governance/licensing: spec CC-BY-SA-4.0 under the nonprofit Modelica Association, implementations from OSMC-PL (OpenModelica) to proprietary (Dymola) — open spec, uneven implementations, no conformance suite. Verdict for the architect: adopt FMI (and possibly SSP) as solver-orchestration interchange; do not extend Modelica into a proof-bearing evidence language — the extension points that exist are exactly the fail-open ones the product's thesis rejects.
