## system

CWL (Common Workflow Language), Nextflow, Snakemake, and WDL — the four dominant scientific workflow systems / workflow description standards

## overlap

These four systems already implement most of the "solver orchestrator" half of the proposed product, at the mechanism level. Typed IO: CWL v1.2.1 declares tool/workflow inputs and outputs with a real type system — primitives, File and Directory objects, records with named fields, arrays, enums, unions — plus `secondaryFiles` patterns for companion files and a `format` field carrying ontology IRIs (e.g. EDAM) for semantic file-format checking; a process "is ready to run when all required input parameters are associated with concrete values" (fail-closed on missing inputs). WDL has a comparable static type system with declared task inputs/outputs. Containerized invocation: CWL `DockerRequirement`, Nextflow's Conda/Spack/Docker/Podman/Singularity support, Snakemake's integrated conda-env/container directives — software environment is part of the declared unit of work in all four. Caching/resume: Nextflow `-resume` hashes session, task name, inputs, script content, container image, and environment into a per-task key stored in LevelDB under `.nextflow/cache`; Snakemake adds experimental between-workflow caching keyed by a Merkle tree over steps, parameters, software stack, and raw inputs. Provenance receipts: CWLProv produces a BagIt research object with SHA-256 content-addressed data, the executable workflow, environment snapshot, and W3C PROV-DM retrospective provenance at four defined levels; Nextflow's nf-prov plugin (v1.6.x) emits BioCompute Objects and Workflow Run RO-Crate. Scheduling and partial results: all four dispatch to HPC schedulers (Slurm/LSF/etc.), Kubernetes, and the major clouds, resume from completed tasks, and keep per-task work directories as inspectable partial results. This is exactly the "heavy solver obligations run as batch jobs" tier of the proposed product: deterministic-ish task hashing, environment pinning, replayable receipts, and failure isolation, hardened by a decade of production use across thousands of pipelines (156 nf-core pipelines alone).

## insufficiency

They orchestrate opaque processes; nothing in any of the four carries the semantics of the computation. Concrete missing mechanisms: (1) Types are wire/filesystem types — File, Directory, string, int, record — not quantities. There is no unit system, no dimensional analysis, no reference frames, no coordinate conventions; CWL's `format` IRI is a label checked for identity against an ontology concept, not a checked semantics of the bytes. A task that expects km and receives miles type-checks. (2) No claim/evidence layer: outputs are files, not typed assertions with distinguished measurement/numerical/parameter/structural uncertainty; "success" is an exit code plus output-glob match. There is no verdict taxonomy — nothing can say proved/supported/out_of_regime; Nextflow/Snakemake distinguish only done/failed/cached. (3) No inference: none of the four can derive anything from results, check model assumptions, or detect that a solver was run outside its validity regime; the DAG is the only logic. (4) Caching is byte-identity, not semantic: Nextflow's docs list NFS timestamp skew, LevelDB single reader/writer, global-variable race conditions, and non-deterministic channel merge order as cache-breaking pitfalls — the hash proves "same bytes were run", never "same mathematical problem was solved", and cannot share work across algebraically equivalent formulations. (5) No proof objects: CWLProv records what ran (retrospective PROV), not why the result follows; its own paper flags Level-2 resource provenance as noisy and it was implemented only in the reference cwltool, not Toil or Cromwell. (6) Tolerances, seeds, and convergence criteria are not first-class: they ride in as ordinary parameters with no schema distinguishing them, so "resource_exhausted vs non_convergent vs numerically_indeterminate" cannot be expressed — a failed solver and a diverged solver look identical.

## narrowing_history

Mixed, and instructive. CWL is the genuine narrowing story: founded 2014 as a vendor-neutral open standard for "describing how to run command line tools and connect them" across all domains, and its site still shows cross-domain ambitions (ELIXIR, EOSC, cloud platforms). In practice adoption concentrated in bioinformatics platforms (Arvados, Seven Bridges/Cavatica, Toil, Kids First), the spec has been frozen at v1.2 (approved 2020-08-07, patch v1.2.1) for six years with no v1.3 visible on the site or spec repo, and its provenance arm (CWLProv) stalled at a cwltool-only implementation — the community's energy moved to Workflow Run RO-Crate instead. It never expanded upward into computation semantics; it deliberately stayed at the command-line-tool boundary, and the two most-used engines in its own field (Nextflow, Snakemake) kept their own DSLs rather than adopting it as their format. WDL narrowed institutionally: Broad's Cromwell repo now states the team "cannot provide direct support" to self-managed instances, develops only AWS/GCP Batch backends with others "community-based", and steers users to the managed Terra platform; spec stewardship passed to a community governance committee, with new community engines (Sprocket, a Rust engine+linter at v0.29.0, targeting 20k concurrent jobs; miniwdl; Toil) carrying it. Nextflow and Snakemake did not narrow — Nextflow grew a company (Seqera) and a 156-pipeline curated ecosystem (nf-core); Snakemake is at v9.25.2 (released 2026-08-18) with steady cadence. The lesson in the narrowing that did happen: a specification without a dominant, funded runtime (CWL) freezes; a runtime without its sponsor's business alignment (Cromwell) decays into a managed-platform funnel.

## adoption

Real, large, and heavily concentrated in bioinformatics/life sciences. Observed on 2026-08-26: Nextflow 3.5k GitHub stars, latest stable 26.04.6 with an active edge channel (26.08.0-edge), and 156 curated nf-core pipelines; Snakemake 2.9k stars, v9.25.2 released 2026-08-18 (eight days before access — very active), with the repo's own claim of ">7 new citations per week in 2021, almost 400k downloads" (self-reported); WDL v1.2.1 spec patch released, README describing v1.3 as current (spec/release discrepancy observed), four conformance-tested engines including the new Rust engine Sprocket at v0.29.0; CWL lists ~6 production engines (cwltool, Toil, Arvados, StreamFlow, Calrissian, CWL-Airflow) but the spec is frozen at v1.2.1 since 2020 and several listed implementations support only v1.0-1.1. Honest reading: Nextflow and Snakemake are the living, growing systems; CWL is an established but stagnant interchange standard; WDL survives via its ecosystem while its original flagship engine (Cromwell) is de-prioritized by its sponsor in favor of the Terra managed platform. Claims of use outside life sciences exist (CWL user gallery) but I saw no comparable pipeline-registry evidence for other domains.

## lessons

Copy: (1) CWL's typed IO contract as the tool boundary — named, typed parameters with File/Directory/record/enum/union types, fail-closed readiness ("ready when all required inputs have concrete values"), secondaryFiles, and container requirement as part of the declared unit — this is the correct shape for the proposed product's solver-obligation interface, and emitting CWL (or WDL) for the batch tier gives free access to every existing engine and scheduler. (2) Nextflow's task-hash design (inputs + script + container + environment into one cache key) and Snakemake's Merkle-tree between-workflow cache as the template for reproducibility receipts — but key them on the compiled IR hash, which the proposed product can make semantic where these cannot. (3) Emit Workflow Run RO-Crate for provenance rather than inventing a receipt format — CWLProv's own trajectory (multi-format PROV serialization judged "an unnecessary burden", single-engine uptake, superseded by RO-Crate profiles that nf-prov now emits) is direct evidence that a bespoke provenance container fails and a lightweight, tooling-supported one spreads. Avoid: CWL's mistake — shipping a specification without a compelling runtime and without any semantics above the process boundary. CWL proved that a permissive, well-typed, conformance-tested standard can still freeze for six years when the value it adds over just using an engine (Nextflow/Snakemake) is portability alone. The proposed product's value must come from what these cannot do (units, claims, uncertainty, verdicts, inference), while delegating what they already do; re-implementing schedulers, container plumbing, and resume logic would burn the 12-month solo budget on solved problems.

## cluster_answer

Roughly 70-80% of the orchestration checklist is already solved and should be adopted or emitted, not re-implemented. Solved and mature: containerized invocation (all four; container identity participates in cache keys), caching/resume (Nextflow's per-task hash over inputs/script/container/environment in LevelDB; Snakemake's Merkle-tree cache over steps/params/software/inputs — though Snakemake marks between-workflow caching experimental), scheduling across HPC/cloud/Kubernetes with per-task work directories as partial results, and provenance capture (CWLProv's BagIt+PROV research objects with SHA-256 content addressing and four provenance levels; nf-prov's BioCompute Objects and Workflow Run RO-Crate). Typed IO is solved at the data-plumbing level: CWL v1.2's File/Directory/record/array/enum types with fail-closed input readiness and ontology-IRI file formats is the best-designed piece and the one most worth adopting directly — the proposed product should compile solver obligations down to CWL CommandLineTool/WDL task documents and let existing engines run them. What they fundamentally lack, uniformly: any semantics of the computation. Types stop at the byte/file boundary — no units, dimensions, frames, or model assumptions; success is an exit code, not a verdict; caching is byte-identity, not problem-identity; provenance says what ran, never what was established or under which validity regime; uncertainty, tolerances, and seeds are undifferentiated parameters, so the proposed disposition taxonomy (non_convergent vs numerically_indeterminate vs resource_exhausted) is inexpressible. CWL adoption honesty: its typed IO model is genuinely conformance-tested across ~6 production engines, but the spec has been frozen at v1.2.1 since 2020, CWLProv was implemented only in the reference cwltool, several listed engines lag at v1.0-1.1, and the two dominant workflow runtimes in CWL's own home field declined to adopt it — adopt its type-model design and its role as emission target, but do not bet on its ecosystem momentum.
