## system

OpenMath (OpenMath Society standard, v2.0 R2 2019) and Content MathML (W3C MathML Chapter 4, incl. Strict Content MathML), with OMDoc/MMT as the statement/theory-level extension

## overlap

OpenMath is the closest prior art to the proposed surface language's vocabulary discipline, restricted to mathematics. Its object model is a tiny term calculus — applications, bindings, attributions over symbols, variables, and literals — where every symbol (OMS) must structurally reference a Content Dictionary (CD) by cd+name: name resolution against declared vocabulary is built into the syntax, and an unresolvable symbol is an invalid object, the same fail-closed instinct as the proposed compiler. CDs are versioned public artifacts carrying per-symbol prose descriptions, formal mathematical properties (FMPs, themselves OpenMath objects), examples, and optional signatures in a "Small Type System" — i.e., a committed, reviewable vocabulary corpus with named symbol semantics, structurally analogous to Nibli's committed predicate corpus. Phrasebooks are the standard's name for per-system typed adapters translating OpenMath objects to each application's internal representation — the exact role of the proposed product's typed solver adapters. SCSCP (v1.3, an OpenMath-Society protocol) is the orchestrator half: an RPC framework in which mathematical systems offer computational services with OpenMath encoding both payloads and protocol instructions (dedicated scscp1/scscp2 CDs), including remote-object references and error returns; implemented in GAP (maintained gap-packages/scscp, GPL-2.0), historically in MuPAD, KANT, Maple prototype, and SCSCP4Mathematica. Strict Content MathML (MathML 3/4 Chapter 4) is an isomorphic XML dialect of OpenMath — csymbol elements reference OpenMath CDs — giving a normalized machine-interpretable core plus a sugared non-strict layer with normative rewrite rules (MathML 4 WD Appendix F), a two-layer spec design (strict kernel + human-friendly surface, deterministic desugaring) the proposed product would replicate. OMDoc extends OpenMath objects with statement and theory levels — definitions, theorems, proofs, theory morphisms — the document/knowledge layer; its living descendant is KWARC's MMT system. What overlaps is therefore: symbol-grounded semantic encoding of mathematics, versioned public vocabulary, per-backend adapters, and a solver-invocation protocol over the same encoding.

## insufficiency

Concrete missing mechanisms, not ambitions: (1) No binding to computational semantics — CD meaning rests on prose descriptions plus FMPs that no tool is required to check, execute, or prove against; two conforming phrasebooks can disagree about a symbol's behavior (branch cuts, partiality, 0^0) while both comply, because OpenMath 2.0 compliance (Chapter 5) is encoding-level (valid XML, lexical error handling, CD reference validity), never semantic. (2) No enforced typing — STS signatures are optional metadata; nothing rejects an ill-typed object at "compile" time. (3) No units, reference frames, or dimensional checking as first-class obligations (units CDs existed only as experimental dictionaries), and no representation of measurement/numerical/parameter/structural uncertainty at all. (4) No result taxonomy or dispositions — SCSCP errors are ad hoc CD symbols; there is no proved/supported/out_of_regime distinction because OpenMath transports terms, it does not adjudicate claims. (5) No proof objects, provenance, or reproducibility receipts — no hashing, no solver identity/version capture, no seeds/tolerances; an OpenMath object is context-free by design. (6) No deterministic evaluation semantics for numerics — float literals have lexical form but no precision/tolerance contract (Fateman's 2001 critique already targeted this). (7) Governance mechanism decayed: the official CD repository's last commit is 2022-06-28, so the extensibility story (new symbols via reviewed CDs) is inoperative in practice. OpenMath is an interchange encoding; the proposed product is a compiler+adjudicator that owns semantics — the entire verdict/uncertainty/receipt layer has no counterpart here.

## narrowing_history

Both halves narrowed, in documented ways. OpenMath began in 1993 workshops and an EU ESPRIT consortium with the ambition of being THE universal semantic interchange between computer algebra systems and for mathematics on the web (1.0 Feb 2000, 1.1 Oct 2002, 2.0 Jun 2004); the ecosystem of grant-funded phrasebooks (INRIA, RIACA, ESPRIT, later the SCIEnce project's SCSCP work, 2006-2011) died with the grants — the openmath.org software page still lists AXIOM 2.3, INRIA C library v1.4a, and ActiveMath as if current. What survived is OpenMath as a semantics registry: the anchor vocabulary for Strict Content MathML and a handful of CAS-composition niches (GAP's SCSCP). The 2017/2019 "Revision 1/2" releases are editorial maintenance of the 2004 standard, not new capability. Content MathML narrowed harder and more explicitly: content markup was half of MathML 1-3 (W3C REC, ISO/IEC 40314), but no browser ever implemented it; when the W3C Math WG restarted in April 2021 it split out MathML Core — "browser-driven design principles" — which by its own text omits content markup entirely and covers only presentation (Chrome shipped it Jan 2023). Content MathML survives normatively in the MathML 4.0 Working Draft (latest 2026-06-04, still WD as of access) but targets "computational systems rather than direct browser rendering" — i.e., the web platform, the one distribution channel that could have forced adoption, formally narrowed to presentation-only. The narrowing driver in both cases: consumers who controlled deployment (browsers, CAS vendors) had no economic reason to implement semantics they didn't need, and the standard had no mechanism to make semantics pay for itself.

## license

Not software, so SPDX applies awkwardly. The OpenMath 2.0 standard text states only "© 2000–2019 The OpenMath Society" with no explicit open license found in the fetched document (evidence-incomplete on exact CD/standard licensing; the CDs repo page fetched did not display a license file). MathML 4 / MathML Core are W3C specifications under the W3C Document/Software licenses (not verified in-task — evidence-incomplete). Distribution model: freely downloadable specs, CDs in a public GitHub repo (OpenMath/CDs), implementations independently licensed — GAP's scscp package is GPL-2.0 (verified on repo page). Practical consequence for the architect: the CD vocabulary content is freely readable and referenceable but its formal reuse terms are unclear; the standard imposes no licensing constraint on an independent implementation.

## adoption

Honest reading of what I observed 2026-08-26: the official OpenMath/CDs GitHub repo has 209 commits, 17 stars, and no commits since 2022-06-28. The OpenMath Society still exists (Helsinki-based, elected executive) and republished the standard as 2.0 Revision 2 in 2019, but the software page is dominated by 1990s-2000s artifacts (AXIOM 2.3 phrasebook, INRIA libraries v1.0-1.4, RIACA services, ActiveMath) with only a Rust crate and py-openmath described as modern. Living consumers actually visible: (1) the W3C MathML 4 Working Draft, which normatively anchors Strict Content MathML symbols on OpenMath CDs via csymbol; (2) GAP's scscp and openmath packages (maintained repo, GPL-2.0, Konovalov/Linton); (3) Wolfram Language, whose Import/Export "fully support the MathML 2.0 specification" including optional Content MathML — note the pin at MathML 2.0, a 2003-era spec, in 2026 documentation. Browsers: zero content-markup support ever; MathML Core (W3C CR; Editor's Draft 27 Jul 2026) excludes it by design. No package-registry or citation counts were gathered; I saw no evidence of any production scientific-computing pipeline consuming OpenMath today. Verdict: the standard is alive as a document and as a semantics registry for MathML's spec text; as an interchange ecosystem it is dormant.

## lessons

Copy: (a) the object-model discipline — a tiny strict kernel term language where every symbol structurally names its defining vocabulary entry, plus a sugared surface with normative deterministic desugaring (Strict vs non-strict Content MathML is a well-worked design for exactly the two-layer compiler the product proposes); (b) versioned public dictionaries carrying per-symbol formal properties and signatures — but make them machine-checked build inputs (the Nibli committed-corpus pattern: in-repo, CI-gated invariants) rather than committee-reviewed external artifacts; (c) SCSCP's insight that solver orchestration should reuse the same typed encoding for payloads, protocol instructions, and errors. Avoid the one structural mistake that killed it: OpenMath positioned itself as a neutral interchange among N sovereign systems, so semantic fidelity depended on N independently-funded phrasebooks it did not control, conformance was encoding-only, and meaning bottomed out in prose. The proposed product must instead OWN the semantics end-to-end — one compiler, typed adapters it maintains itself, external solvers as contracted backends whose answers are adjudicated (verdict + disposition + receipt), never peers exchanging terms. And never let a vocabulary entry exist whose semantics is only a description string: bind every symbol to something checkable (type, unit, axiom, executable contract) or refuse it — OpenMath's FMPs show that unchecked formal properties decay into documentation.

## cluster_answer

Who consumes it today: observably, (1) the W3C MathML 4 Working Draft itself, which uses OpenMath CDs as the semantic ground for Strict Content MathML — a spec consuming a spec; (2) GAP, via the maintained scscp/openmath packages for CAS composition; (3) Wolfram Language, which imports/exports Content MathML but pins at MathML 2.0; (4) residual e-learning/formula-search lineages I could not verify in-task. Browsers — the only mass deployment channel — never implemented content markup, and MathML Core formally excludes it. The official CD repo has been dormant since June 2022. Failure mechanism, in order of causal weight: FIRST, no binding to computational semantics — conformance was encoding-level, FMPs were unchecked prose-adjacent metadata, so implementing OpenMath bought a system syntax interchange without meaning interchange; the hard problems (branch cuts, partiality, precision, assumptions/context) were exactly what the lowest-common-denominator encoding dropped, as Fateman's 2001 critique predicted. SECOND, the phrasebook burden: N systems x M dictionaries of translation code, written mostly by grant-funded third parties (ESPRIT, RIACA, INRIA, SCIEnce) rather than by vendors with a business need — the adapters died when the grants did. THIRD, CD governance: extensibility-by-reviewed-dictionary meant the official vocabulary froze at MathML2-era school mathematics while real semantics scattered into experimental/private CDs, reintroducing the ambiguity the standard existed to remove. Lesson for any "universal scientific IR": an IR without an owned, checkable evaluation/verification semantics is a serialization format, and serialization formats survive only where a deployment channel forces them. Do not build a neutral interchange awaiting phrasebooks; build one system whose IR is internal, whose vocabulary is machine-gated at compile time, whose adapters you write and test yourself, and let interchange be an export, not the product.
