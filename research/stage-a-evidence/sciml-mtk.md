## system

Julia ModelingToolkit.jl (MTK) and the SciML ecosystem: Symbolics.jl (CAS layer over SymbolicUtils.jl), DifferentialEquations.jl (solver suite), Catalyst.jl (reaction-network DSL), all under the SciML GitHub organization; commercial development concentrated at JuliaHub (JuliaSim).

## overlap

MTK is the closest existing thing to the proposed product's mathematics/physics core, at the mechanism level. Users declare typed symbolic variables (with metadata including units), write declarative equation systems, and MTK compiles them: it performs alias elimination, tearing of nonlinear systems, and automatic DAE index reduction, then generates optimized numerical code (Jacobians, Hessians, sparsity exploitation) handed to independent solver backends — OrdinaryDiffEq/DifferentialEquations.jl (ODE/SDE/DAE/DDE/jump), NonlinearSolve.jl, Optimization.jl, MethodOfLines.jl/NeuralPDE.jl for PDEs. That is exactly the "model compiler + solver orchestrator" split: a symbolic front-end with deterministic-ish transformations delegating heavy numerics to typed backend problem/solver interfaces (SciMLBase's problem types are a de-facto typed solver-obligation IR). It supports acausal (Modelica-style) component composition with a lazy connection system and flattening — the compositional physics-modeling capability the proposed product would need. Symbolics.jl supplies symbolic mathematics (differentiation, simplification, symbolic equation solving) in the same substrate, so symbolic and numeric layers share one expression type. Unit validation runs automatically at system construction against DynamicQuantities-annotated variables, refusing dimensionally inconsistent equations — a partial analog of the proposed compile-time unit checking. Catalyst.jl shows the domain-DSL pattern the product would want for chemistry/biology: a reaction-network surface language compiling through the same symbolic system to ODE/SDE/jump semantics, published in PLOS Computational Biology (2023). MTK v10 (JuliaCon 2025) unified ODESystem/SDESystem/NonlinearSystem/JumpSystem into a single `System` type on the insight that these are one representation with optional fields — directly relevant IR-design prior art. Solver results carry structured return codes (success/divergence/maxiters-style), a rough precursor of the proposed disposition axis. Scale: MTK 1.7k stars, 11,389 commits, 530 open issues; DifferentialEquations.jl 3.2k stars; the stack is the de-facto standard for equation-based scientific modeling in Julia and underpins JuliaHub's commercial JuliaSim.

## insufficiency

Concrete missing mechanisms, not ambitions: (1) No proof objects anywhere — symbolic transformations (simplify, index reduction, tearing) are rewrite passes with no certificate, checkable derivation, or logical semantics; correctness rests on the test suite. There is no logical inference engine at all: no entailment queries, no closed-world reasoning, no verdict like proved/disproved — results are numbers plus exceptions/retcodes. (2) No fail-closed vocabulary: `@variables`/`@parameters` mint symbols ad hoc in an open namespace; a typo creates a new unknown rather than a compile error; there is no declared lexicon, no reference frames, no model-assumption declarations to omit. (3) Units are optional in practice and check-only: variables without unit metadata validate trivially, `checks = ~ModelingToolkit.CheckUnits` disables validation, the FAQ recommends `t_nounits`/`D_nounits` as the default independent variable, validation "merely checks that the equations are consistent" (no conversion), supports only scalar quantities, and generated numerical code runs on unitless floats — units never reach the solver. (4) No provenance/reproducibility receipts: reproducibility is environment-level (Julia Project/Manifest pinning); no per-result hash of source/IR/generated code, no recorded solver identity+version+seed+tolerance replay artifact. (5) No evidence/uncertainty model as first-class claims: Measurements.jl/MonteCarloMeasurements.jl compose generically through the type system but collapse to value±error propagation; measurement vs numerical vs parameter vs structural uncertainty are not distinguished anywhere in the core. (6) Not a linkable library: requires the Julia runtime and JIT (compile-latency, not embeddable from Rust/C as a small deterministic component); determinism of compilation output is not a stated contract. (7) The full structural-simplification compiler (post-v11) is AGPL, outside the permissive core.

## narrowing_history

The modeling scope did not narrow — it broadened (v10's unified `System` type absorbed dynamic optimization, JuliaCon 2025). Three real narrowings, with evidence: (a) LICENSING/OPENNESS: on 2025-12-06 the SciML Steering Council announced the MTK v11 split — ModelingToolkitBase stays MIT with basic codegen, while advanced compiler passes (the full `structural_simplify`/`mtkcompile`) moved to AGPL-licensed, JuliaHub-hosted libraries. Stated reason: "several large companies are leveraging MTK for commercial work, but not participating in the open source ecosystem," and without JuliaHub sponsorship active development would cease — i.e., the permissive core was economically unsustainable and the differentiating compiler was enclosed (discourse.julialang.org thread 134396). Catalyst v16 consequently re-targeted ModelingToolkitBase "to avoid adding new, non-MIT licensed dependencies" and accepts a less-featured compile path. (b) UNITS: current validation docs are exclusively DynamicQuantities, scalar-only, degrees unsupported — a narrower contract than full quantity arithmetic (the earlier Unitful-based path's deprecation is evidence-incomplete, but the docs' DynamicQuantities-only state is observed). (c) PDEs: PDESystem exists but discretization was delegated to satellite packages (MethodOfLines.jl, NeuralPDE.jl) rather than delivered in the core compiler.

## adoption

Strong, observable: MTK 1.7k stars, 263 forks, 11,389 commits, 113 open PRs; DifferentialEquations.jl 3.2k stars with Zenodo DOI and a formal citation policy; Symbolics.jl 1.5k stars; Catalyst.jl 527 stars, 6,188 commits, PLOS Computational Biology 2023 paper. Release cadence is fast and current: stable docs v11.26.7 built 2026-05-31; releases page shows v11.40.0 dated Aug 25 (page year extraction ambiguous; 2026 by inference from the docs timeline). A commercial company (JuliaHub) funds most MTK contributors — both an adoption signal and, per the Dec 2025 sustainability announcement, a fragility: large commercial users reportedly do not contribute back. Counterweight: 530 open issues on MTK and 484 on Symbolics indicate a large defect/feature backlog; three breaking major versions in roughly two years (v9→v10 in 2025→v11 in late 2025/2026) impose churn on downstreams (Catalyst v16 is itself a breaking re-target).

## lessons

Copy: the compiler/solver separation with typed problem objects as the obligation interface (SciMLBase problem types); acausal component composition with lazy connections and flattening; automatic index reduction/tearing as compiler passes (this is genuinely hard, decades of Modelica literature — do not underestimate it); the v10 lesson that one unified system representation with optional fields beats N parallel system types; unit checking at system-construction time; structured solver return codes as a disposition precursor; domain DSLs (Catalyst) compiling through a shared core. Avoid: (1) permissive-by-default validation — MTK's units are disablable, trivially satisfied by unannotated variables, and the recommended path is unitless, so in practice most models are unchecked; the proposed fail-closed posture is exactly the opposite and is a real differentiator. (2) The sustainability trap: a permissively-licensed core whose hardest component is funded by one company ended with the differentiating compiler enclosed under AGPL — decide the funding/licensing model before, not after, commercial adoption. (3) Breaking-version churn (v9/v10/v11 in ~2 years) that forces the ecosystem to fork its dependency graph. (4) Environment-level reproducibility only — Manifest pinning is not a per-result receipt; MTK shows nobody in this space ships one, which is open ground.

## cluster_answer

SciML already delivers most of the symbolic-numeric mechanics of the proposed mathematics/physics core: declarative equation systems, a real CAS, acausal composition, structural simplification (alias elimination, tearing, index reduction), code generation, and orchestration into the broadest open-source differential-equation solver suite that exists, plus reaction-network chemistry via Catalyst. Rebuilding that compiler in Rust is a multi-year effort on its own. What it structurally lacks is precisely the proposed product's identity: no proof objects or logical inference of any kind (transformations are uncertified rewrites; there is no proved/disproved verdict, only numbers and retcodes); an open, fail-open vocabulary (symbols minted ad hoc, typos become fresh unknowns); no provenance receipts (Manifest-level environment pinning, no per-result source/IR/artifact hashes, solver identities, seeds, tolerances); and no first-class evidence/uncertainty model (Measurements.jl-style value±error propagation, uncertainty kinds conflated). Units: validation is on by default at system construction via DynamicQuantities (current docs reference DynamicQuantities exclusively; Unitful survives only in the wider ecosystem), but it is effectively optional — unannotated variables pass vacuously, `checks = ~CheckUnits` disables it, the FAQ recommends the `t_nounits` path, only scalars are supported, and generated numerical code is unitless, so units never constrain the solve. Correctness/maintenance reputation, observably: very active (v11.x releases through Aug 2026, 11k+ commits) and widely used (3.2k/1.7k/1.5k stars, Zenodo DOI, published papers), but carrying 500+ open issues on MTK alone, repeated breaking major versions, the 2022 Vishnevsky ecosystem-correctness criticism (general Julia, partially SciML-adjacent; a 2024 follow-up reports most cited issues fixed — detail evidence-incomplete), and a Dec 2025 funding crisis that moved the advanced compiler behind AGPL. Verdict for the architect: not redundant — the proposed product's differentiators (proofs, receipts, fail-closed vocabulary, uncertainty taxonomy) are all absent here — but its solver-orchestration and structural-simplification layers are prior art to study closely, and its licensing history is a warning about funding a permissive core.
