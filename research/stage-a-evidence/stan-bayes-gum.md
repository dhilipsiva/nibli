## system

Stan (stanc3 compiler + CmdStan/interfaces) and the Bayesian-workflow ecosystem around it: PyMC (Python PPL on PyTensor), ArviZ (exploratory analysis + the InferenceData schema), anchored for measurement uncertainty by the JCGM/GUM metrology documents (JCGM 100:2008 GUM, JCGM 101:2008 Monte Carlo supplement, JCGM 200:2012 VIM).

## overlap

Stan overlaps the proposed product at the mechanism level more than any other surveyed system. (1) Typed declarative surface with fail-closed compilation: a Stan program is six ordered blocks (functions, data, transformed data, parameters, transformed parameters, model, generated quantities) of declared, typed, constrained variables (`real<lower=0>`, simplex, covariance matrices); scope is declaration-before-use, "each variable's value is validated against its declaration as it is read," and the stanc3 compiler (OCaml) runs an explicit typecheck phase before lowering to an IR and generating C++ — undeclared identifiers and type mismatches are compile errors, never defaulted. (2) Deterministic compilation to a lower-level artifact (C++), with the compiler a separate, versioned component (default since Stan 2.26). (3) Orchestrator shape: one model artifact is dispatched to multiple inference algorithms (NUTS/HMC, ADVI, Pathfinder, L-BFGS optimization) — solver choice is separated from model statement, and run configuration carries seeds, step sizes, and adaptation parameters. (4) Machine-readable result diagnostics: rank-normalized split R-hat (threshold 1.01), bulk/tail ESS, MCSE, divergent-transition counts, treedepth saturation, E-BFMI — all emitted per-run. (5) A cross-backend typed result schema: ArviZ's InferenceData is a formally documented specification (xarray DataTree groups: posterior, prior, sample_stats, observed_data, log_likelihood, predictions, unconstrained_posterior) with standardized sample_stats variable names (`diverging`, `energy`, `tree_depth`, `reached_max_treedepth`, `step_size`, `lp`) — the closest shipped analog to the product's typed result/receipt object, shared by Stan and PyMC outputs. (6) Evidence-with-uncertainty as the entire point: observed data enters a declared measurement model and parameter uncertainty exits as a posterior — the one surveyed system where empirical claims and their uncertainty are the primary computation, not an annotation.

## insufficiency

Missing mechanisms, not ambitions. (1) No unit or dimension system: Stan's type lattice is int/real/complex/containers plus range constraints — `real<lower=0> mass;` and `real<lower=0> seconds;` are the same type; dimensional errors compile and sample. No reference frames, no quantity kinds (VIM concepts absent). (2) One uncertainty ontology: everything representable must become a probability distribution over declared parameters. Measurement uncertainty is expressible only as a modeling idiom (a known-sigma error model); nothing in the language marks a scale as "measurement" vs "parameter," so the distinction is authorial convention, invisible to tooling. Structural uncertainty is not representable at all — a Stan program is one model; the candidate-model set exists only in the analyst's file system, compared post hoc via LOO/stacking in ArviZ/loo. (3) No proof objects and no logical inference: results are samples plus diagnostics; there is no derivation, no entailment checking, no symbolic math. (4) No verdict/disposition separation: a run yields draws plus warnings; "converged but model is wrong" and "did not converge" surface through the same diagnostic channel (see cluster answer). (5) Provenance is partial: seeds and Stan version ride the output CSV, and InferenceData can carry them, but there is no source/IR/artifact hash chain, no solver-identity binding across the compiler seam, no replay receipt — reproducibility is a practice (make + version pinning), not an emitted artifact. (6) Workflow discipline is extralinguistic: the Bayesian Workflow paper (arXiv:2011.01808) explicitly presents iterative model building, checking, and comparison as informal applied practice, not software-enforced structure — prior predictive checks, SBC, and comparison conventions live in ArviZ function conventions and community norms, not in the language or its result types.

## narrowing_history

Stan itself did not narrow from a wider ambition — it has been "full Bayesian inference via NUTS/HMC, plus ADVI and penalized MLE" continuously; its notable exclusions (no discrete parameters — marginalize by hand; no units; no model-set objects) are original design boundaries, not retreats. The measurable narrowing in the ecosystem is PyMC's: after Theano's 2017 end-of-life, PyMC attempted a ground-up PyMC4 on TensorFlow Probability and publicly abandoned it in 2020 ("The Future of PyMC3, or: Theano is Dead, Long Live Theano," pymc-devs Medium; github.com/pymc-devs/pymc4 is archived-deprecated: "Official work on this project has been discontinued"), with TF's eager mode named as the main obstacle; the team instead took over Theano maintenance (now PyTensor) — a retreat from "rebase on a big-ecosystem backend" to "own the compilation backend," which succeeded (PyMC now at 6.3.1 on PyTensor with C/JAX compilation). stanc3's "experimental support for other outputs like TensorFlow" likewise never displaced the C++ target. ArviZ's 1.0 (2024–2026 line, 1.3.0 released 2026-08-11) refactored the monolith into a metapackage over ArviZverse subpackages — a modularization, not a scope cut.

## lessons

Copy: (1) the constrained-type discipline — declare-then-validate-at-read, constraints as both error checks and intent, a separate typechecking compiler phase (stanc3's lex→parse→typecheck→IR→codegen is exactly the product's proposed pipeline shape); (2) InferenceData wholesale — a documented, backend-neutral schema with standardized diagnostic variable names is the existing wire format for "machine-readable solver diagnostics"; the product's receipts should be able to embed or emit it rather than invent a rival; (3) Stan's own validity-vs-efficiency partition of warnings (divergences/R-hat/ESS = validity, treedepth = efficiency) as the seed of a disposition taxonomy; (4) PyMC's backend lesson — own the compilation backend you depend on (the abandoned TFP rewrite vs. the successful Theano takeover) — directly relevant to a solo-dev orchestrator delegating to external solvers. Avoid: (1) leaving workflow discipline outside the language — the Bayesian Workflow paper is 77 pages of practice that its own authors could not formalize into software; anything the product wants enforced (uncertainty-kind separation, out-of-regime declarations) must be in the type system, because convention demonstrably does not hold; (2) collapsing uncertainty kinds into one posterior object — Stan shows that once everything is a distribution over parameters, tooling can no longer tell measurement from prior belief; (3) shipping diagnostics without bound interpretation — Stan emits `diverging` counts but the folk-theorem knowledge ("this probably means your model is wrong") lives in blog posts and docs, not in the result object.

## cluster_answer

Per uncertainty kind, as typed machine-readable objects: PARAMETER uncertainty — fully solved: declared parameters get posterior distributions, typed and serialized in InferenceData's posterior group with per-parameter R-hat/ESS/MCSE; this is the state of the art the product must match, not invent. NUMERICAL uncertainty — diagnosed but not propagated: MCSE quantifies Monte Carlo error per estimate; divergences, ESS, E-BFMI, treedepth are typed per-draw/per-run objects (sample_stats: `diverging`, `energy`, `tree_depth`, `reached_max_treedepth`), effectively a shipped non_convergent/numerically_indeterminate disposition record — but ODE/algebra-solver tolerances, while settable, leave no trace in results, and nothing composes numerical error into downstream claims. MEASUREMENT uncertainty — representable only by idiom (a known-sigma error model); the language cannot distinguish a measurement-error scale from any other parameter, so it is not a typed object. STRUCTURAL uncertainty — not represented at all: one program is one model; comparison (LOO, stacking) is post hoc across artifacts with no model-set object. Entanglement evidence: Gelman's folk theorem — "when you have computational problems, often there's a problem with your model" (2008 blog post; restated in arXiv:2011.01808) — is precisely the claim that the disposition non_convergent is usually evidence for the verdict invalid_model; Stan's own diagnostics page classifies divergences as a validity concern whose primary remedies are reparameterization or model change, i.e. the ecosystem's most important diagnostic cannot be mechanically filed under either axis. Treedepth, by contrast, is documented as "an efficiency concern," showing a partial disentangling already exists. Stacking-vs-BMA (Yao/Vehtari/Simpson/Gelman 2018, with published discussion) shows structural uncertainty has no settled semantics in the M-open case — BMA weights are incoherent when no candidate is true — so a "conflicting" verdict across models has no canonical aggregation to inherit. What GUM binding adds that Stan omits: Type A ("statistical analysis of series of observations") vs Type B ("means other than") evaluation as a provenance tag on every uncertainty component — Stan renders a calibration-certificate uncertainty and a subjective prior as indistinguishable objects; GUM adds degrees of freedom per component, uncertainty budgets as auditable decompositions, combined/expanded uncertainty with coverage factors, VIM-controlled vocabulary, and JCGM 101 as an existing normative spec for Monte Carlo propagation with tolerance reporting (GUM is current and maintained: Amd.1:2026 just addressed model nonlinearity). Novelty verdict for the product: the claim "no prior art on the solving side" is FALSE as stated — Stan is shipped prior art for typed parameter uncertainty and machine-readable numerical diagnostics — but the narrower claim survives: no shipped system types the FOUR kinds distinctly or keeps them distinct through inference; measurement-kind typing (GUM-bound) and structural-kind representation are genuinely unshipped, and the folk theorem warns that the verdict/disposition separation the product promises is exactly where this ecosystem's 18-year failure history sits.

## largest_unverified_assumption

That the four uncertainty kinds CAN be kept distinct through inference at all. Stan's history is evidence against, not merely absence of evidence: once measurement, prior, and parameter uncertainty enter a joint posterior they are mathematically fused, the folk theorem shows numerical and structural failure are empirically entangled, and stacking-vs-BMA shows structural uncertainty lacks agreed semantics even among the field's leaders. No fetched source demonstrates any system preserving the four-way separation end-to-end; the product's core claim is therefore untested, not just unshipped.
