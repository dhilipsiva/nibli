## system

Isabelle/HOL (incl. AFP entry "A Sound Type System for Physical Quantities, Units, and Measurements") and Coq/Rocq (incl. Mathematical Components, CoqInterval/Flocq validated numerics)

## overlap

Both assistants already implement the proposed product's logical core at mechanism level. (1) Typed declarative KR with fail-closed resolution: every identifier must be declared before use; Isabelle's HOL type system and Rocq's dependent types make ill-typed statements compile errors, never defaults. Compilation/checking is deterministic. (2) Exact inference with proof objects: Rocq's kernel checks a full proof term for every theorem; Isabelle's LCF-style kernel forces every theorem through a small trusted inference core. This is the strongest existing implementation of "proved" as a verdict backed by an artifact. (3) Dimensioned quantities: the AFP Physical_Quantities entry (Foster & Wolff, Oct 2020) encodes ISQ dimensions as type parameters (base-dimension exponent vectors at the type level) so that only same-dimension quantities can be equated, with tactic support for the quantity-algebra congruences and type-safe SI↔Imperial conversion — i.e., unit soundness as a compile-time typing discipline, exactly the product's "missing units are compile errors" stance. (4) Validated numerics: CoqInterval proves real-number inequalities by reflection — a verified interval/Taylor-model evaluator (over Flocq floating point, configurable precision) is executed by the kernel's reduction machinery; tactics `interval`, `integral`, `root` turn numeric bound claims into machine-checked theorems. (5) Solver orchestration: Isabelle's Sledgehammer is a mature orchestrator that ships goals to untrusted external ATPs/SMT solvers (E, Vampire, Z3, cvc5) and then reconstructs their answers through the trusted kernel — the untrusted-oracle-plus-checked-reconstruction pattern the product's "typed external solvers" needs. (6) Symbolic mathematics libraries at scale: MathComp's algebra hierarchy (basis of the Odd Order and Four Colour proofs) and Isabelle/HOL's analysis libraries. (7) Reproducibility regime: the AFP is a curated, versioned archive re-checked in CI against each Isabelle release — a working, if implicit, provenance/replay discipline for formal artifacts.

## insufficiency

Missing mechanisms, not ambitions: (1) No evidence semantics. Everything is a theorem or nothing; there is no typed representation of empirical claims, no measurement/parameter/structural uncertainty kinds, and no verdicts like supported/refuted/conflicting/out_of_regime — the assistants' judgment space is {proved, not-yet-proved}. (2) No result-disposition taxonomy: a failed Sledgehammer call or a `vm_compute` timeout is an interactive error message, not a structured disposition (resource_exhausted, non_convergent, backend_unavailable) a program can consume. (3) No machine-readable reproducibility receipts: solver identities/versions/seeds/tolerances used by Sledgehammer are not bound into the resulting theorem; reconstruction deliberately discards them. (4) Not linkable from Rust: Isabelle is ML+Scala, Rocq is OCaml; neither kernel is packaged as an embeddable library with a stable C ABI, and checking their proof objects requires the full kernel (definitional unfolding, universes) — Isabelle does not even record proof terms by default. (5) Reflection-based numerics (CoqInterval) yields no transferable certificate: the "proof" is a computation trusted to the assistant's own reduction engine, so an external product cannot consume it without re-trusting or reimplementing that evaluator. (6) No simulation/ODE/batch-solver delegation with typed contracts; CoqInterval covers bounded real inequalities and 1-D integrals over recognized operators, not general numerical models. (7) Authoring cost: interactive proof requires expert users; there is no seconds-latency declarative surface a domain scientist can use fail-closed without proof engineering.

## narrowing_history

Isabelle did narrow, by ecosystem gravity rather than decree: it began (Paulson, 1980s) as a generic logical framework — Isabelle/Pure hosting multiple object logics (FOL, ZF, HOL, CTT) — but usage consolidated onto Isabelle/HOL, where all the automation (simp sets, Sledgehammer) and the entire AFP accreted; the multi-logic ambition survives in architecture but not in practice [inference from architecture docs and AFP composition; not separately sourced]. The lesson: automation and libraries compound in one logic and starve the others. Coq/Rocq did not narrow — it broadened from a type-theory checker into mathematics (MathComp), software verification, and extraction; the 2025/2026 Coq→Rocq change was a rename, not a scope change (rocq-prover.org describes the same system, formerly the Coq Proof Assistant). CoqInterval itself is an example of deliberate narrowness succeeding: one maintainer (Melquiond), one problem class (real-expression bounds), sustained for ~two decades across assistant versions.

## lessons

Copy: (a) the AFP units design — dimensions as compile-time type-level exponent vectors with congruence normalization, proving that unit soundness belongs in the compiler, not the solver; (b) Sledgehammer's architecture — untrusted external solvers as oracles whose output is re-checked by a small trusted core, never trusted on identity alone; (c) the LCF discipline — a minimal kernel through which every verdict must pass; (d) AFP's CI-re-checked, versioned archive as the germ of reproducibility receipts. Avoid: (e) reflection-only numerics — CoqInterval's verdicts are locked inside the assistant because the certificate IS the trusted computation; the product must make every heavy backend emit an externally checkable certificate (subdivision trace, SOS identity, LRAT/Alethe proof) instead; (f) requiring interactive proof skill for ordinary use — this is the single cause of the assistants' adoption ceiling despite 40 years of maturity; (g) treating everything as a theorem — with no typed empirical-evidence layer the assistants structurally cannot say "supported" or "out_of_regime", and bolting that on later is impossible because the kernel's judgment space is fixed.

## cluster_answer

Dimensioned quantities: the state of the art inside assistants is the AFP entry Physical_Quantities (Foster & Wolff, 2020, BSD): ISQ/SI deeply embedded in Isabelle's type system, quantities parameterized by dimension types (base-vector exponents), same-dimension-only equality, tactic support for quantity-algebra congruences, SI/Imperial conversions. No comparably adopted units library exists on the Rocq side [evidence-incomplete]. Teaching: units are a static typing/normalization problem — implement them in the product's own compiler; there is nothing to delegate. Validated numerics: CoqInterval proves real-expression bounds by reflection — a formally verified interval/Taylor evaluator over Flocq floats executed by the kernel's reducer. This is the crucial negative lesson for certificate consumption: reflection produces NO transferable certificate; the verdict is inseparable from the assistant's reduction engine. So an external product should not try to consume assistant-internal numeric proofs. What IS practical for a Rust checker are solver-native certificate formats where checking is far cheaper than search and the checker is small: (1) DRAT/DPR/LRAT for SAT — rate is an existing Rust/MIT checker faster than drat-trim; LRAT/GRAT are designed for simple checkers. (2) Alethe for SMT (emitted by veriT and experimentally by cvc5) — Carcara is an existing Rust/Apache-2.0 checker and elaborator (TACAS 2023); Alethe is also reconstructible in Isabelle and via SMTCoq, so one certificate can serve both the product's Rust checker and later assistant-grade audits. (3) For nonlinear/numeric obligations, the checkable-certificate analogue is a witness the checker replays with its own interval arithmetic: SOS/Positivstellensatz identities (check = polynomial identity + PSD verification), or branch-and-bound subdivision traces with per-cell bounds (the Flyspeck pattern). Full kernel proofs (Rocq terms, Isabelle proofterms) are impractical to check without embedding the assistant: they need definitional unfolding, universe checking, and Isabelle doesn't record proof terms by default [inference]. Architecture conclusion: verdict + solver-native certificate + small independent Rust checker per format; use assistants (via Alethe/SMT-LIB bridges) as optional high-assurance auditors, never as the product's runtime.

## largest_unverified_assumption

That there is no practical, maintained pipeline for exporting Isabelle or Rocq proofs (including CoqInterval-style reflective numeric results) as compact certificates checkable outside the assistant's kernel — I verified the reflection design and the default absence of Isabelle proof terms only indirectly, and did not survey export frameworks like Dedukti/Lambdapi or Isabelle's export_theory, which could partially weaken the claim that assistant proofs are unconsumable by a Rust checker.
